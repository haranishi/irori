# 設計：対戦ゲーム第1弾

## 判断とUX5階層
- 戦略：友人同士が会話しながら遊ぶ。反射神経より、相手の選択を読む楽しさを増やす。
- 要件：チャンバラ2人、カード2〜8人、1勝負で完結し、既存の再戦へ戻れる。
- 構造：説明 → 秘密選択 → 一斉公開 → 次の手 → 結果。切断等は復帰待ちへ分岐。
- 骨格：上に進行、中央に対戦／灯と札、下にルールの要点。スマホは選択と確定確認を主役にする。
- 表層：チャンバラは刀の抽象形と火花、灯市は灯と札。既存の囲炉裏の暖色を受け継ぐ。
- 受け入れ：初見の人がスマホの選択だけで参加し、公開結果から理由と次の行動を判断できる。

## 実装境界
各ゲームは `logic.js`（純粋判定）、`main.js`（SDK接続）、`view.js`（描画）、CSSとHTMLを持つ。
状態・イベント・効果をJSDocで型付けし、DOMやSDKを単体判定に持ち込まない。
既存 `ten-seconds` を境界の参考にするが、新規の共通フレームワークは作らない。
`setPad(spec, seat)` を使用し、秘密の手を全員宛へ送らない。
開始・次・復帰は1ボタンのpad、手の選択はchoices、確定後はwaitへ置換する。
進行操作と選択肢のIDには勝負nonceと改訂番号を入れ、同じIDを再利用しない。
対応SDKのcapabilitiesを確認し、旧ホストでは更新案内を出す。

## 状態と結果
段階は intro／choose／reveal／recover／ended。
名簿は開始時に固定する。現在のonlineと開始時の全員を分け、消えた席の結果も保持する。
未確定の選択以外は公開モデルに変換して描画する。公開前の生状態はviewへ渡さない。
中断は現在の未確定選択だけを破棄し、公開済みの結果を再適用しない。
復帰後は接続・表示・メニューの全条件がそろってから進行役のやり直しを許す。
終了効果は1回だけ送り、購読とイベントを解除する。未成立はoutcome=incompleteにする。
両ゲームとも得点は大きい方が上位。blade-duelは残り体力、lantern-marketは獲得した灯の価値。

## 分担と制約
- 実装A：`games/blade-duel/**`、対応するregistryのJSONのみ。
- 実装B：`games/lantern-market/**`、対応するregistryのJSONのみ。
- メイン：仕様・登録の統合、サムネイル、型検査対象、既存テストの棚順、E2E、文書、Git。
- レビュー：実装担当と別の担当が読み取りで確認。体験は実ブラウザ、見た目は画像で評価する。
- SDK・通信・Worker・共有や認証の変更、新規依存、外部素材、公開デモは対象外。
- 改善は最大3周、同一失敗2周で残件を記録する。

## 採用理由
ポーカーは個人宛の手札表示が可能だが、役判定・賭け順・退出時の分配までの検証範囲が広い。
今回は異なる人数と読み合いが楽しめる2本を完成させ、ポーカーは次の独立した仕様で扱う。
即時アクション型は回線差が勝敗へ影響するため、チャンバラも同時選択にする。
抽象的な仕組みを参考にしつつ、商品ごとの表現やカード構成を複製しない。

## 検証
純粋判定で全組合せと保存則、旧ID、重複、資源不足、同時決着、10手／6市、復帰と退出を確認。
E2Eは本物の中継とホストを通し、本人だけのpad・共用画面の秘匿・結果と再戦を確認する。
既存の全自動ゲートを実行し、決定的な新規判定を一時的に壊して試験の検出力を確認する。
画像は3幅で閲覧し、ゲーム体験と画面評価の根拠・制約をハーネス実行記録に残す。
