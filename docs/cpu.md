# 既存ゲームへCPUの席を足す

CPUはゲームの中だけに置く。コンソールの名簿・スマホ・結果の記録には追加しない。
人が足りないときも、進行役の「はじめる」から通常の手順で遊ぶ。

## 席と補充

- `fillSeats(humans)` は追加する席だけを返す。人数は整数の0〜8。人が元の最小人数m未満なら推奨人数rまで補い、m以上なら空の配列。
- ババ抜きはm=2・r=4、大富豪はm=3・r=4。登録の `players.min` は人の人数なので1。
- 人の席IDはSDKの正の数値。数値で席順を比較するゲームではCPUに `-1`、`-2` …を使う。名前は `CPU 1` …、`cpu:true`、`online:true`。
- CPUの一覧は局の作成時に固定する。名簿更新にも同じCPUを結合し、途中の増減で補充し直さない。次の局で決め直す。
- 負のIDは判定と画面だけで使う。SDKの `look` にも渡さず、専用の灰白色のロボット図形を描く。

## 頭に渡す情報

- `logic.js` の `viewFor(state,seat)` は公開モデル＋本人の手札＋本人用padだけを複製する。他席の手札、乱数状態、山札、伏せ札との対応を含めない。
- `cpu.js` の `decide(view,seat,rng)` は本人用ビューだけから、通常の入力と同じ形を返す。選べない段階は `null`。
- `view.self` と席が違えば拒否する。本人用padのtokenと札IDをそのまま使い、古い入力を組み直して送らない。
- `rng` は呼び出し側が保持する種つき乱数。決定と `thinkMs(rng)` に実時計や `Math.random` を使わない。
- 思考時間は800〜2000ms。ババ抜きは伏せた札の位置を無作為に選ぶ。
- 大富豪は既存の合法手列挙を再利用し、場に合う弱い札から選ぶ。同じ強さは乱数。8切り・革命は序盤に温存し、終盤や他に手がないときに使う。出せなければ場があるときだけパスする。

## mainのドライバー

1. `players` とCPUを結合して `createGame` と名簿イベントへ渡す。
2. CPUごとに乱数の列を持つ。操作できるpadがある席だけ `thinkMs` 後の予約を作る。
3. 発火時に最新の `viewFor` を取り直して `decide` し、通常の `input` イベントへ渡す。
4. 状態の変更では古い予約を全て取り消して再予約する。停止・切断・非表示のpadは操作不可なので予約しない。
5. 終了・ページ破棄でも予約を取り消す。画面の演出用時計とCPUの思考時間は別に管理する。
6. `pad`・`vibrate`・`end.results` は人だけに絞ってSDKへ渡す。画面にはCPUを含む公開モデルを渡す。

## 試験

- 元の最小人数〜8席を各2000局、全段階の合法手と終了を検査する。
- 人1＋CPUを2000局、CPUだけを2000局、人だけの局、同じ種の結果を検査する。
- 他席の秘密を同じ枚数の別の札へ交換しても、本人用ビューが変わらないことを検査する。ビューの変更がstateへ戻らないことも検査する。
- 停止中・番以外・終了後の `null`、思考時間の上下限、予約の取消し・最新ビューの再取得を検査する。
- mainを実際の判定へ接続し、再開から結果まで進める。SDKにCPUのIDや記録が届かず、結果の画面にはCPUが残ることを検査する。
- ブラウザでは `?mock=1` の開始〜結果と、人数充足時の補充なしを確認する。画像だけで進行成功とは判断しない。

## 見つかった落とし穴

- 数値を前提にする判定へ文字列IDを混ぜると、席順と次の番が壊れる。
- 名簿イベントへ人だけを渡すと、判定がCPUの退出として扱う。
- 古いpadから入力を作るとtokenが合わない。発火直前に取り直す。
- CPUへpadを送らないだけでは足りない。番・革命・上がりの振動をmainで作るゲームも、宛先を人に絞る。
- SDKの結果にはCPUを載せないため、ゲーム自身の結果表示を残す必要がある。
- 登録の英語summaryは80文字まで。CPUの説明は既存文を短くして収める。
- 数値の並びで配札や番を決めるゲームでは、負のCPU IDが席順へ影響する。勝率は人数と席位置を併記し、全席が同じ確率とは扱わない。
