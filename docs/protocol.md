# 中継は何も解釈しない配管にして、ゲームの状態はホストだけが持つ

サーバーが知っているのは「部屋」「席」「誰がつながっているか」だけ。ゲームの規則も得点も持たない。スマホの入力はホストへ運び、ホストの指示（コントローラーの画面や振動）はスマホへ運ぶ。型と上限値の正本は [`packages/protocol`](../packages/protocol/src) にあり、この文書は意味と理由を書く。

## つなぎ方

| 入口 | 役割 |
|---|---|
| `POST /api/rooms` | 部屋を作り、4文字のコードとホストの鍵を返す。同じIPの回数と1日の総数に上限がある。`Origin` が自分のホストと違う要求（別のサイトのページから）は 403 |
| `GET /api/rooms/:code` | 部屋の有無・ロック・人数だけを返す。スマホが参加画面を出す前に使う |
| `GET /api/rooms/:code/ws` | WebSocket。ホストもスマホもここにつなぎ、最初のフレーム `hello` で役割を名乗る。部屋の有無に関わらず、同じIPの受け付けの回数に上限があり、`Origin` が違うと 403 |
| `GET /api/health` | 生死の確認。試験と監視に使う |

`hello` が5秒以内に届かない接続は閉じる。役割は最初のフレームで固定し、途中では変えられない。フレームは1つが1つのJSONで、バイナリは使わない（人が読めて、試験で作りやすく、毎秒数十個の小さな入力には十分なため）。

## 部屋と席

コードは `23456789BCDFGHJKLMNPQRSTVWXYZ` から4文字（約70万通り）。母音を除いたのは、不都合な単語ができにくくするため。0/1/O/Iに似た文字も外した。コードは秘密ではなく、鍵でもない。推測で入られても、ホストの画面に参加者が見え、ホストが外せる。

- 席番号は1〜8。入った順に空いた最小の番号を渡す。色と形は画面側が席番号から決めるので、サーバーは見た目を知らない。
- スマホは入るたびに「再開の札」を受け取り、`sessionStorage` に持つ。切れたら同じ札で入り直すと同じ席に戻る。席は切断から60秒残り、過ぎると空いて札も無効になる。
- 同じ札が二重につながったら新しいほうを残し、古いほうを `replaced`（4009）で閉じる。古い接続が半端に残っているだけのことが多いため。閉じられた側は、自動では入り直さない（複製したタブが互いを追い出し続けるため）。画面に「ほかの画面で開かれました」と出し、押したときだけ入り直す。
- ホストは作成時にもらった鍵で入り直せる。サーバーは鍵のハッシュだけを持つ。ホストが落ちている90秒の間、スマホには「ホストを待っています」が出る。過ぎたら部屋を閉じる。
- ロックされた部屋と満員の部屋には、新しい人が入れない。席を持つ人の再接続は通る。

## 検証と上限

受け取ったフレームはすべて、必ず検証を通す。形式や速さが通らないものは捨てて違反に数え、5秒の窓で20回目に接続を切る。ゲームもスマホも、ここでは信用しない。

- 大きさはスマホ512バイト、ホスト16KiBまで。超えたフレームは数えず、その場で接続を閉じる（4002）。速さは、スマホが毎秒60個・瞬間120個、ホストが毎秒40個・瞬間80個まで。
- 数値は範囲に丸める（スティック -1〜1、タッチ 0〜1、傾きは度）。識別子は小文字・数字・`_-` の24文字まで。
- 名前は中継が整える。制御文字と文字の向きを変える文字を除き、空白は畳み、12書記素・32符号位置・96バイトの、先に届いたところで切り、重複には番号を付ける。受け手（ホストと画面）の検査は、符号位置とバイトだけで行う。書記素の数え方は実行環境のICUの版で違い（ミャンマー・クメール・ジャワ・バリ文字の結合子音を、Node 24は2つ、ブラウザは1つと数える）、受け手が書記素で縛ったとき、名前1つで名簿ごと捨てて、ホストが部屋に戻れなくなったため。画面側は必ず `textContent` で描く。
- 部屋ごとに、`hello` 前の接続は同時16本まで（超えた新しい接続はすぐ閉じる）、新しい席は1分に40まで（札での入り直しは数えない）、ロックの切り替えは1分に20まで。入退室とロックのたびに保存の書き込みが出るので、その回数を縛る。
- 入力の頻度は、スマホ側がスティックとタッチを毎秒20回、傾きを15回までに間引き、値が変わらないあいだは送らない（ただし、スティックとタッチを押している間は、約1秒ごとに同じ値を送り直す。離した知らせが届かないまま接続が死んでも、ゲームが止められるように）。Cloudflareは、受け取ったメッセージ20通を1リクエストとして課金するので、いちばん効く節約になる（見積もりは [operate.md](operate.md)）。

## 捨てた案

- **WebRTCを先に作る**：STUNとTURNの運用が要り、学校や職場の回線では接続に失敗する経路を最初から抱える。まず必ずつながる経路を作り、遅延を実測してから足す（[ADR 0002](decisions/0002-websocket-first.md)）。
- **サーバーがゲームの状態を持つ**：ゲームごとにサーバーのコードが要り、制作者がホストの画面だけで完結できなくなる。早押しの順番は、サーバーの受信時刻 `T` を添えて渡すだけにした。
- **ホストの鍵をURLに載せる**：画面共有やスクリーンショットで漏れる。鍵はホストのブラウザの `sessionStorage` にだけ置く。
- **部屋を永続化する**：「前回の続き」は便利だが、保存・削除・個人情報の扱いが増える。部屋は最長12時間、無操作20分で消える。

## 落とし穴

- iOSのSafariは、画面ロックやタブの切替でWebSocketを黙って切る。再接続は例外ではなく通常の経路として設計した。
- Durable Objectは、接続が静かなときにメモリを手放す。名簿は接続ごとの付属情報から組み直し、再開の札だけを保存に書く。
- `T` はサーバーの受信時刻で、押した時刻ではない。回線の遅れが違う人の間では、早押しの公平さを保証しない。
